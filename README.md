# 📚 Library Management API

A RESTful Library Management API built with **Node.js, Express, TypeScript, and MongoDB/Mongoose**.

This project manages books, borrowing transactions, inventory updates, and borrowed-book summaries. It was built to practice backend development concepts such as **REST APIs, Mongoose models, MongoDB ObjectIds, CRUD operations, validation, and aggregation pipelines**.

---

## ✨ Features

- 📖 Create and manage books
- 🔍 Retrieve books
- ✏️ Update book information
- 🗑️ Delete books
- 📚 Borrow books
- 📦 Automatically decrease available copies after borrowing
- 🔄 Automatically update book availability
- 📊 Generate a borrowed-books summary
- 🔗 Use MongoDB `ObjectId` references between collections
- 🧮 Use MongoDB aggregation operators such as `$group`, `$sum`, `$lookup`, `$unwind`, and `$project`
- ✅ Request validation with Mongoose
- 🕒 Manual `createdAt` and `updatedAt` timestamp`

## 📁 Project Architecture

The application follows a layered backend architecture:

```text
Client / Postman
       │
       ▼
    Routes
       │
       ▼
  Controllers
       │
       ▼
    Services
       │
       ▼
    Models
       │
       ▼
    MongoDB
```

### Responsibility of each layer

**Routes**

Define the API endpoints and connect them to controllers.

**Controllers**

Handle HTTP requests and responses.

**Services**

Contain the main business logic.

**Models**

Define the structure of MongoDB documents using Mongoose schemas.

**MongoDB**

Stores the actual application data.

## 📦 Data Models

The application uses two main collections:

```text
books
borrowedBooks
```

### 1. Book

The `Book` collection stores the current state of each book.

Example document:

```json
{
  "_id": "64ab3f9e2a4b5c6d7e8f9012",
  "title": "The Theory of Everything",
  "author": "Stephen Hawking",
  "genre": "SCIENCE",
  "isbn": "9780553380163",
  "description": "A book about the universe and theoretical physics.",
  "copies": 5,
  "available": true,
  "createdAt": "2026-09-20T10:00:00.000Z",
  "updatedAt": "2026-09-20T10:00:00.000Z"
}
```

### 2. BorrowedBook

The `BorrowedBook` collection stores borrowing transactions.

Example document:

```json
{
  "_id": "68c123456789abcdef123456",
  "book": "64ab3f9e2a4b5c6d7e8f9012",
  "quantity": 2,
  "dueDate": "2026-10-15T00:00:00.000Z",
  "createdAt": "2026-09-21T12:00:00.000Z",
  "updatedAt": "2026-09-21T12:00:00.000Z"
}
```

The `book` field stores the `_id` of the corresponding Book as a MongoDB `ObjectId`.

# 📕 Borrow a Book

## Endpoint

```http
POST /api/borrow
```

### Request body

```json
{
  "book": "64ab3f9e2a4b5c6d7e8f9012",
  "quantity": 2,
  "dueDate": "2026-10-15T00:00:00.000Z"
}
```

### Borrowing process

When a user borrows a book, the service performs the following steps:

```text
Receive book ID and quantity
          │
          ▼
Find the requested Book
          │
          ▼
Check whether the Book exists
          │
          ▼
Check available copies
          │
          ▼
Calculate new copy count
          │
          ▼
Update Book
          │
          ▼
Create BorrowedBook record
```

For example:

```text
Current copies = 10
Borrow quantity = 2

New copies = 10 - 2
           = 8
```

The Book is then updated:

```json
{
  "copies": 8,
  "available": true
}
```

If the resulting number of copies is `0`, availability becomes `false`.

Conceptually:

```ts
const newCopies = book.copies - quantity;

available = newCopies > 0;
```

# 🔗 MongoDB ObjectId Relationship

The `BorrowedBook` model uses an ObjectId reference to the `Book` model:

```ts
book: {
  type: Schema.Types.ObjectId,
  ref: "Book",
  required: true
}
```

This means the `book` field stores the MongoDB `_id` of a Book document.

Conceptually:

```text
BorrowedBook
     │
     │ book = ObjectId(...)
     ▼
   Book
     │
     └── _id = ObjectId(...)
```

### Why `ObjectId` matters

MongoDB's `_id` is normally an `ObjectId`.

These two values may look identical:

```text
"64ab3f9e2a4b5c6d7e8f9012"
```

and

```text
ObjectId("64ab3f9e2a4b5c6d7e8f9012")
```

but they are different BSON types.

For MongoDB operations such as `$lookup`, the types need to match.

A common problem is:

```text
BorrowedBook.book → String
Book._id          → ObjectId
```

In that situation, a `$lookup` may fail to find the corresponding book.

The correct relationship is:

```text
BorrowedBook.book → ObjectId
Book._id          → ObjectId
```

# 📊 Aggregation Pipeline

The borrowed-books summary uses a MongoDB aggregation pipeline:

```text
BorrowedBook
     │
     ▼
  $group
     │
     ▼
  $lookup
     │
     ▼
  $unwind
     │
     ▼
  $project
     │
     ▼
Final Summary
```

The pipeline can be represented as:

```ts
const result = await BorrowedBook.aggregate([
  {
    $group: {
      _id: "$book",
      totalQuantity: { $sum: "$quantity" }
    }
  },
  {
    $lookup: {
      from: "books",
      localField: "_id",
      foreignField: "_id",
      as: "bookInfo"
    }
  },
  {
    $unwind: "$bookInfo"
  },
  {
    $project: {
      _id: 0,
      book: {
        title: "$bookInfo.title",
        isbn: "$bookInfo.isbn"
      },
      totalQuantity: 1
    }
  }
]);
```

---

## 1. `$group`

The first stage groups borrowing records by Book ID.

```ts
{
  $group: {
    _id: "$book",
    totalQuantity: { $sum: "$quantity" }
  }
}
```

Suppose the database contains:

```text
Book A → quantity 2
Book A → quantity 1
Book B → quantity 3
Book A → quantity 2
```

After `$group`:

```text
Book A → totalQuantity: 5
Book B → totalQuantity: 3
```

### Important detail

After:

```ts
_id: "$book"
```

the Book ID is stored in the aggregation result's `_id` field.

So the result conceptually becomes:

```json
{
  "_id": "64ab3f9e2a4b5c6d7e8f9012",
  "totalQuantity": 5
}
```

This is why the next `$lookup` uses:

```ts
localField: "_id"
```

rather than:

```ts
localField: "book"
```

---

# 2. `$sum`

`$sum` calculates the total quantity.

```ts
totalQuantity: {
  $sum: "$quantity"
}
```

For example:

```text
2 + 1 + 2 = 5
```

The result is:

```json
{
  "totalQuantity": 5
}
```

---

# 3. `$lookup`

`$lookup` connects the aggregated borrowing information with the `books` collection.

```ts
{
  $lookup: {
    from: "books",
    localField: "_id",
    foreignField: "_id",
    as: "bookInfo"
  }
}
```

The relationship is:

```text
Aggregation _id
      │
      │ matches
      ▼
Book _id
```

The result initially contains an array:

```json
{
  "_id": "64ab3f9e2a4b5c6d7e8f9012",
  "totalQuantity": 5,
  "bookInfo": [
    {
      "title": "The Theory of Everything",
      "isbn": "9780553380163"
    }
  ]
}
```

---

# 4. `$unwind`

Because `$lookup` produces an array, `$unwind` converts the array element into an object.

Before:

```json
"bookInfo": [
  {
    "title": "The Theory of Everything",
    "isbn": "9780553380163"
  }
]
```

After:

```json
"bookInfo": {
  "title": "The Theory of Everything",
  "isbn": "9780553380163"
}
```

This makes it easier to access:

```text
bookInfo.title
bookInfo.isbn
```

---

# 5. `$project`

The final `$project` controls the shape of the response.

```ts
{
  $project: {
    _id: 0,
    book: {
      title: "$bookInfo.title",
      isbn: "$bookInfo.isbn"
    },
    totalQuantity: 1
  }
}
```

The final structure becomes:

```json
{
  "book": {
    "title": "The Theory of Everything",
    "isbn": "9780553380163"
  },
  "totalQuantity": 5
}
```

`_id: 0` removes MongoDB's aggregation `_id` from the response.

`totalQuantity: 1` keeps the field.

# 🔄 Updating Book Documents

When updating an existing Book, Mongoose's `findByIdAndUpdate()` can be used:

```ts
await Book.findByIdAndUpdate(
  id,
  {
    ...payload,
    updatedAt: new Date()
  },
  {
    new: true,
    runValidators: true
  }
);
```

### Important options

#### `new: true`

Returns the updated document.

Without it, Mongoose may return the document from before the update.

#### `runValidators: true`

Runs the schema validators during the update.

#### `updatedAt: new Date()`

Because this project manages timestamps manually, the service updates `updatedAt` whenever the document changes.

---

# 🕒 Manual Timestamps

The Book schema uses:

```ts
createdAt: {
  type: Date,
  default: Date.now
},

updatedAt: {
  type: Date,
  default: Date.now
}
```

This means:

- `createdAt` is generated when the document is created.
- `updatedAt` receives its initial value when the document is created.
- `updatedAt` must be manually changed when the document is updated.

Example:

```ts
{
  ...payload,
  updatedAt: new Date()
}
```

This project intentionally does not use:

```ts
{ timestamps: true }
```

because the timestamps are handled manually.

# 🧠 Important Concepts Learned

## Model vs Document

A Mongoose model represents the collection and provides database operations:

```ts
Book.find()
Book.findById()
Book.findByIdAndUpdate()
Book.create()
```

A document represents one actual record:

```ts
const book = await Book.findById(id);

book.copies;
book.title;
book.author;
```

So:

```ts
Book.copies
```

is incorrect because `Book` is the model.

Whereas:

```ts
book.copies
```

refers to the property of one retrieved document.

---

## Express Route Parameters

If the route is:

```ts
router.get("/:id", controller);
```

the value is accessed using:

```ts
req.params.id
```

If the route is:

```ts
router.get("/:bookid", controller);
```

then:

```ts
req.params.bookid
```

The parameter name comes directly from the route definition.

---

## `findByIdAndUpdate()`

The basic structure is:

```ts
Model.findByIdAndUpdate(
  id,
  update,
  options
);
```

Example:

```ts
await Book.findByIdAndUpdate(
  id,
  {
    copies: newCopies,
    available: newCopies > 0
  },
  {
    new: true,
    runValidators: true
  }
);
```

The method does not require manually fetching the Book first if the only goal is to update it.

# 🗃️ Database Design

The two collections have different responsibilities.

### `books`

Stores the current inventory state:

```text
Book
├── title
├── author
├── genre
├── isbn
├── description
├── copies
├── available
├── createdAt
└── updatedAt
```

### `borrowedBooks`

Stores borrowing transactions:

```text
BorrowedBook
├── book
├── quantity
├── dueDate
├── createdAt
└── updatedAt
```

This separation allows the system to keep:

```text
Current inventory
        +
Borrowing history
```

as separate pieces of data.

# 🐛 Common Problems and Solutions

## `$lookup` returns an empty array

Check:

1. Is the collection name correct?
2. Is `localField` correct?
3. Is `foreignField` correct?
4. Are both fields the same BSON type?
5. Is the Book actually present?

For this project, the important relationship is:

```text
BorrowedBook.book → ObjectId
Book._id          → ObjectId
```

---

## Schema changed but old data still fails

Changing a Mongoose schema does not automatically convert documents already stored in MongoDB.

For example, if old documents contain:

```text
book: "64ab..."
```

and the new schema expects:

```text
book: ObjectId("64ab...")
```

the existing document is still stored as a string.

For development/testing, old test documents can be deleted and recreated.

For a production database, a proper data migration would be required.
